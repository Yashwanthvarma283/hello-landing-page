- All server-side AI calls go through `supabase/functions/_shared/ai-pool.ts` (admin primary key + `ai_usage_logs` logging); pass `req` so usage is attributed to the user. Why: one admin-controlled key and complete per-user/feature analytics.
- The IDE chatbot provider is a global server setting (`ai_settings.ide_use_primary`), never browser storage; raw API keys never reach the client. Why: settings must apply to all users and keys must stay secret.
- This project runs on Lovable Cloud (backend attached 2026-10-30); the old external Supabase is disconnected and its data was not migrated. All schema changes go through the database migration tool (never hand-write files under `supabase/migrations/` or `supabase/manual-sql/`). Why: the migration tool journals, validates and applies changes directly.
- Legacy tables predate the Data API grant requirement: when adding a new public table, always add GRANTs (authenticated/service_role) and RLS policies in the same migration. Why: the backfill in migration 0012 covers existing tables only.
- AI calls that used to hit the Lovable gateway use `supabase/functions/_shared/ai-compat.ts` (`aiGatewayFetch`), which routes through ai-pool and turns forced tool-calls into JSON mode. Why: the external backend has no gateway key, and JSON mode is more reliable than tool calling across providers.
